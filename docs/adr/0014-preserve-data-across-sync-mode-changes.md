# 0014: Preserve data across sync mode changes

Changing between local-only mode and iCloud sync will merge records by stable identity instead of replacing one collection with another. Snip Snap will compare the local and server records with their last shared version and merge fields that changed on only one side. When both sides changed the same user field differently, the current server value remains on the original snip and Snip Snap saves the local value as a recovered snip. Device and upload dates will not choose a winner. Attachments merge by stable identity, and ordering resolves in a fixed way. This favors visible extra data over silent loss.

## Consequences

A recovered snip waits in a Needs Attention review, which the Mac panel header and the iOS library offer while any are pending. On iOS it also appears as a badged row at the top of its list. It keeps a link to the current snip and records the fields that conflicted. The review compares the two versions and offers Keep Current, Use Recovered, Keep Both, and Edit. Keep Both adds the recovered version to its list, or to Inbox when that list no longer exists. A choice changes only conflicting fields and must refresh if the current snip changed while the review was open. Review does not open as an urgent prompt, and a pending review is not a sync issue. Other records keep syncing; later edits to the reviewed snip or list wait until the review is settled.

When a remote delete competes with an offline edit, the original remains deleted and the edited version becomes a recovered snip in Inbox. When a remote edit reaches iCloud before CloudKit accepts an offline deletion, the edit wins, even if the deletion is already queued: the deleting device restores the current server version of the snip or list, with the attachments it still holds, withdraws its deletion, and settles without a review or sync issue. The user can delete it again. A deletion CloudKit has already accepted stands, because CloudKit deletes do not check for newer edits. If a remote list deletion competes with an offline move into that list, the list remains deleted and the snip moves to Inbox. Snips in a list deleted on another device also move to Inbox. Neither move is a sync issue, and Snip Snap does not yet explain it. Manual order uses sync-safe sort keys with stable IDs as tie-breakers. A server-accepted update settles concurrent reorders within one list without a recovered copy or warning. Concurrent moves of one snip to different lists conflict like any other field and produce a recovered snip.

A user may turn off sync while offline by copying the current local cache after the app warns that newer iCloud changes may be absent. Turning off sync leaves the iCloud copy intact. Settings reports sync as off, setting up, on, syncing, or turning off, and names an issue when one needs attention. It does not promise that all remote changes have arrived.

## Sync-mode activation

On enable, Snip Snap fetches iCloud and merges it with the device's library before swapping the active store. The first upload uses the normal outbound queue after the swap. The device keeps its original library writable while preparing the candidate. Turning off sync copies the device's library and leaves iCloud content in place. This replaces the original copy-then-upload activation (#419).
