# Switching between lists: iOS and Mac

Research date: 2026-09-23

## Recommendation

On iPhone, keep the existing visible list picker and row swipe actions. Prototype list switching as a gesture that **starts at a screen edge** and moves inward, only on the list-content screen. Give the leading edge to the existing Back or sidebar navigation gesture wherever a navigation stack uses it; in that state, use a visible list picker or the opposite edge rather than overriding Back. This follows Apple's guidance to keep standard navigation available, avoid system-gesture conflicts, and treat custom gestures as shortcuts with another way to perform the same action. It is a design recommendation, not an Apple-prescribed sibling-list gesture. ([Gestures](https://developer.apple.com/design/human-interface-guidelines/gestures/), [UINavigationController interactive pop gesture](https://developer.apple.com/documentation/uikit/uinavigationcontroller/interactivepopgesturerecognizer))

An edge **origin** matters. A horizontal swipe that begins on a row and merely travels *toward* the edge is still competing with that row's swipe action. Apple defines row actions by the horizontal edge from which the row is swiped, while `UIScreenEdgePanGestureRecognizer` is specifically for motion starting near a screen edge. ([SwiftUI row swipe actions](https://developer.apple.com/documentation/swiftui/view/swipeactions(edge:allowsfullswipe:content:)), [UIKit screen-edge pan](https://developer.apple.com/documentation/uikit/uiscreenedgepangesturerecognizer))

On Mac, use SnipSnap's existing **bottom horizontal tab strip** as the primary route. Add **Previous List** and **Next List** menu commands with keyboard shortcuts; consider small previous/next buttons beside the strip if rapid switching needs a pointer target. A trackpad page swipe can be explored as an optional accelerator, but should not be required: Mac input includes mouse and keyboard, and users can configure trackpad page-swipe behavior. Apple's Mac guidance asks for menu commands, keyboard shortcuts, and multiple ways to move between pages. ([SnipSnap tab strip](../../SnipSnap/SnipListTabBarView.swift), [Designing for macOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-macos/), [Mac Catalyst: navigation](https://developer.apple.com/design/human-interface-guidelines/mac-catalyst/), [Pointing devices](https://developer.apple.com/design/human-interface-guidelines/pointing-devices/), [Trackpad settings](https://support.apple.com/guide/mac-help/change-trackpad-settings-mchlp1226/mac))

## Evidence and limits

| Pattern | Primary-source evidence | What it establishes |
| --- | --- | --- |
| Row swipe actions | Apple documents `swipeActions` for a list row, including actions on both leading and trailing sides. Apple's Mail guide says users can swipe a message left or right to reveal or perform actions. ([SwiftUI](https://developer.apple.com/documentation/swiftui/view/swipeactions(edge:allowsfullswipe:content:)), [Mail for iPhone](https://support.apple.com/guide/iphone/organize-email-in-mailboxes-iph376ef8aa3/ios)) | This is a standard action on an item, so SnipSnap's row gestures should retain priority for touches starting in the row. |
| Edge navigation | UIKit's built-in navigation controller pops a view from a swipe beginning at the **leading** screen edge. Apple's sidebar guidance cites the built-in edge swipe on iPadOS for sidebar access. ([UIKit](https://developer.apple.com/documentation/uikit/uinavigationcontroller/interactivepopgesturerecognizer), [Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars/)) | Edge swipes already carry navigation meaning. An app-defined sibling-list switch must defer to an active Back/sidebar gesture. |
| Adjacent pages | SwiftUI provides a paged `TabView`; Apple's page-control guidance discusses navigation among flat pages on iOS and says page controls are not supported on macOS. ([PageTabViewStyle](https://developer.apple.com/documentation/swiftui/tabviewstyle/page), [Page controls](https://developer.apple.com/design/human-interface-guidelines/page-controls/)) | Paging is a supported iOS model, but a full-width page swipe would overlap SnipSnap's row swipe actions. A page control does not transfer directly to Mac. |
| Mac navigation | Apple's pointing-device guidance lists “swipe between pages” for a mouse or trackpad; Mac Catalyst guidance explicitly recommends Next/Previous buttons alongside trackpad gestures and top-level navigation in the View menu. ([Pointing devices](https://developer.apple.com/design/human-interface-guidelines/pointing-devices/), [Mac Catalyst](https://developer.apple.com/design/human-interface-guidelines/mac-catalyst/)) | An optional trackpad gesture is plausible, but a command and visible route should carry the feature. |

I found no Apple first-party documentation showing **edge swipes directly changing sibling lists while those lists also have row swipe actions**. The closest documented combination is Mail's row swipes plus the platform's separate leading-edge Back navigation. This is an inference from the cited sources, not proof that no app implements the exact gesture. ([Mail for iPhone](https://support.apple.com/guide/iphone/organize-email-in-mailboxes-iph376ef8aa3/ios), [UIKit navigation](https://developer.apple.com/documentation/uikit/uinavigationcontroller/interactivepopgesturerecognizer))

## Prototype checks

1. Confirm row swipes still reveal their actions when started in row content, including a row close to either edge. ([SwiftUI row swipe actions](https://developer.apple.com/documentation/swiftui/view/swipeactions%28edge%3Aallowsfullswipe%3Acontent%3A%29))
2. Confirm the leading-edge Back/sidebar transition still works on every navigation depth and size class where the system supplies it. ([UIKit navigation](https://developer.apple.com/documentation/uikit/uinavigationcontroller/interactivepopgesturerecognizer), [Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars/))
3. Keep the selected list visible in a control, announce the new list for assistive input, and make list switching available without a gesture. ([Gestures](https://developer.apple.com/design/human-interface-guidelines/gestures/), [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility/))
4. For Mac, verify menu commands and shortcuts while focus is in the list, composer, search field, and bottom tab strip. Avoid assigning a shortcut that conflicts with a system command. ([SnipSnap tab strip](../../SnipSnap/SnipListTabBarView.swift), [Keyboards](https://developer.apple.com/design/human-interface-guidelines/keyboards), [SwiftUI menu bar](https://developer.apple.com/documentation/swiftui/building-and-customizing-the-menu-bar-with-swiftui))
